# M4.1 Design Contract — Movement Domain Foundation

## 1. Purpose and Scope

M4.1 establishes the domain foundation for movement. It defines the movement state, command, result, and error contracts that later M4 steps will build upon.

M4.1 does **not** implement the pathfinding algorithm, reachable-cell UI, hover path preview, or full movement interaction.

The existing `M4_DESIGN_CONTRACT.md` remains the source of truth for the complete M4 movement rules. This document freezes the architectural decisions specific to M4.1.

Refinements agreed before M4.2 are recorded in [§15 Forward Notes for M4.2](#15-forward-notes-for-m42). Sections 2–14 remain the record of M4.1.

## 2. Movement State

A unit owns both its initial movement allowance and its current remaining allowance:

```ts
interface Unit {
    // ...
    moveRange: number;
    remainingMovement: number;
}
```

`moveRange` is the unit's initial movement allowance. It is not consumed by movement.

`remainingMovement` is current battle state and is reduced by successful movement.

The invariant is:

```text
0 <= remainingMovement <= moveRange
```

When movement is initialized or reset:

```text
remainingMovement = moveRange
```

After a successful movement:

```text
remainingMovement' = remainingMovement - movementCost
```

The model must support multiple movement actions before movement is reset, so a future turn can support sequences such as:

```text
MOVE → ATTACK → MOVE
```

Combat is not part of M4.1.

## 3. State vs Derived State

`remainingMovement` is intentionally stored as explicit state on `Unit` rather than being derived from movement history.

Reasons:

- it directly represents the current battle state;
- immutable state transitions can update it explicitly;
- future mechanics can consume or restore movement without coupling the model to a movement-history representation;
- the model remains independent of a future persistence/event-sourcing strategy;
- the current battle state can be transferred or reconstructed without requiring the frontend to replay movement history.

The domain must maintain the invariant between `moveRange` and `remainingMovement`.

A future event-sourced implementation may reconstruct this state from events or snapshots, but event sourcing is not introduced in M4.1.

## 4. MoveUnitCommand

Movement is requested through a command containing the unit, destination, and the exact path selected by the caller:

```ts
type MoveUnitCommand = {
    type: 'MOVE_UNIT';
    unitId: string;
    destination: Position;
    path: readonly Position[];
};
```

The path contains the cells entered during the movement and **does not contain the starting position**.

Therefore:

```text
path[0]                    = first entered cell
path[path.length - 1]      = destination
```

The command expresses:

> Move this unit to this destination using this exact path.

The engine remains authoritative. A supplied path is never trusted without validation.

At minimum, command validation must eventually verify that:

- the unit exists;
- the unit is allowed to move in the current demo context;
- the path is non-empty;
- the path ends at `destination`;
- every path transition is legal;
- the complete footprint is valid at every path position;
- diagonal transitions obey the no-corner-cutting rule;
- the total path cost is within `remainingMovement`.

The detailed path rules are defined by `M4_DESIGN_CONTRACT.md` and will be implemented in M4.2/M4.3.

## 5. Why the Command Contains the Path

The command deliberately carries the selected path rather than only the destination.

This allows the player eventually to choose between multiple valid paths with the same minimum cost:

```text
        selected unit
              |
              v
      calculate possible paths
          /           \
       path A        path B
       cost 4        cost 4
          \           /
           \         /
            player chooses
                  |
                  v
        MOVE_UNIT(destination, path)
```

The engine must still validate the selected path.

This design also leaves room for future mechanics whose behaviour depends on the route taken, without requiring the current milestone to implement such mechanics.

M4.1 does not require the UI to present multiple path choices.

## 6. Movement Result

A successful movement should return both the resulting battle state and useful information about what was executed:

```ts
interface MovementResult {
    state: BattleState;
    path: readonly Position[];
    cost: number;
}
```

The command expresses what the caller requested. The result expresses what the engine actually executed.

For the current implementation, the returned path will normally be the validated path from the command.

Returning the path is useful because it gives the caller the authoritative executed route without requiring it to retain or reconstruct the command.

Returning the cost is useful because movement cost is a domain rule and the frontend should not independently recalculate it.

The frontend can therefore display information such as:

```text
Movement cost: 3.41
Remaining movement: 1.59
```

without duplicating movement-cost rules.

## 7. Execute Result

The movement execution API should use a result type rather than throwing for normal invalid gameplay commands:

```ts
Result<MovementResult, MovementError>
```

A failed movement must not partially mutate the battle state.

The exact `Result` implementation should follow existing project conventions. Do not introduce a new Result abstraction if the project already has an appropriate one.

## 8. MovementError

For M4.1, `MovementError` should be represented as a TypeScript discriminated union.

The exact members should remain small and should follow the project's existing error conventions. A possible starting shape is:

```ts
type MovementError =
    | { type: 'UNIT_NOT_FOUND'; unitId: string }
    | { type: 'UNIT_CANNOT_MOVE'; unitId: string }
    | { type: 'INVALID_DESTINATION'; destination: Position }
    | { type: 'INVALID_PATH'; reason: string }
    | { type: 'INSUFFICIENT_MOVEMENT'; required: number; available: number };
```

Do not prematurely create a large hierarchy of highly specific path errors in M4.1. More specific cases may be introduced in M4.2 if they improve correctness, testing, or UI handling.

Possible future refinements include distinguishing blocked paths, out-of-bounds paths, invalid diagonal transitions, and footprint collisions.

## 9. Domain Boundaries

Movement rules belong in `BattleEngine` or framework-independent domain helpers called by it.

Angular components and the SignalStore must not implement movement rules directly.

The intended flow is:

```text
Angular interaction
      |
      v
SignalStore/application layer
      |
      v
BattleEngine.execute(...)
      |
      v
Result<MovementResult, MovementError>
      |
      v
new BattleState + authoritative movement information
```

The movement domain must not depend on:

- Angular;
- DOM APIs;
- HTTP;
- Spring;
- JPA;
- browser-specific rendering.

## 10. Immutability

Successful movement produces a new immutable `BattleState`.

The previous state must remain unchanged.

The movement transition changes at least:

- the moved unit's anchor position;
- the moved unit's `remainingMovement`.

The unit's footprint and `moveRange` remain unchanged.

No other unit should be modified by a movement command.

## 11. Backend Considerations

Because `remainingMovement` is part of the battle domain state, the backend battle model will eventually need to represent it as well when the authoritative battle engine moves to Java.

M4.1 does **not** move movement execution to the backend.

Likewise, future combat will likely introduce current/remaining health as battle state, but that is not part of M4.1.

The frontend implementation should therefore keep the domain model clear enough that it can later be represented by the Java backend without coupling it to Angular.

## 12. Future Path Selection

M4.1 intentionally separates three concepts:

1. path calculation;
2. path selection by the player;
3. path validation/execution by the engine.

M4.2 will implement minimum-cost pathfinding and reachability.

Later frontend work may expose more than one equally cheap path and allow the player to choose one. M4.1 must not introduce a UI for this prematurely, but the `MoveUnitCommand` must be capable of carrying the chosen path.

## 13. Out of Scope for M4.1

Do not implement the following as part of M4.1 unless a minimal dependency is unavoidable and explicitly discussed:

- Dijkstra or A*;
- reachable-cell calculation;
- footprint-aware pathfinding;
- diagonal corner blocking implementation;
- movement highlighting;
- hover path preview;
- movement-cost labels;
- technical reset UI;
- real turns;
- attacks;
- persistence;
- event sourcing;
- backend-authoritative movement;
- multiplayer.

## 14. M4.1 Acceptance Criteria

M4.1 is complete when:

1. `Unit` contains `moveRange` and `remainingMovement` with the defined semantics.
2. `MOVE_UNIT` is represented as a command containing `unitId`, `destination`, and `path`.
3. The path excludes the starting position and ends at the requested destination.
4. Movement execution uses `Result<MovementResult, MovementError>`.
5. `MovementError` is a discriminated union following project conventions.
6. `MovementResult` contains the resulting `BattleState`, executed path, and movement cost.
7. A successful movement can update the unit position and remaining movement without mutating the previous state.
8. `moveRange` remains unchanged by movement.
9. The domain API does not depend on Angular or browser APIs.
10. Existing M1–M3.5 behaviour remains intact.
11. Pathfinding and movement UI remain outside the M4.1 implementation scope.

## 15. Forward Notes for M4.2

The following refinements were agreed in the M4.2 pre-implementation design review. Where they differ from the sections above, they apply from M4.2 onwards.

### 15.1 Current player (§2, §9)

`BattleState` gains `currentPlayer: PlayerSide`. It was not part of M4.1.

In M4.2 the frontend mapper initializes `currentPlayer` to `LEFT` because the demo API does not carry it yet. This is a temporary fixture default, not frontend ownership of turn state. In M5, `currentPlayer` becomes part of the backend/API battle state and the mapper maps it instead.

A unit may move only when `unit.owner === state.currentPlayer`; otherwise the engine returns `UNIT_CANNOT_MOVE`. The engine reads the value from `BattleState` and never assumes `LEFT` itself.

### 15.2 Remaining movement (§2)

Movement costs remain `number`. Budget checks use a single tolerance, so a path whose cost equals the remaining movement up to floating-point rounding is allowed.

After a successful movement:

```text
remainingMovement' = max(0, remainingMovement - movementCost)
```

Clamping at `0` keeps the invariant `0 <= remainingMovement` intact when the tolerance accepts such a path.

### 15.3 Command and path validation (§4, §5)

`MoveUnitCommand.path` stays `readonly Position[]`. The caller supplies only the chosen cells; costs are always computed by the engine.

In addition to the list in §4, a command is valid only if:

- the unit can occupy `destination` with its complete footprint;
- the path is a **simple path**: every path position is distinct and the starting position does not occur in the path. Loops and paths returning to the start are rejected;
- every footprint cell along the path has a terrain entry. A cell without one is treated as non-traversable.

The simple-path rule applies to a single `MOVE_UNIT` command. A later movement in the same turn may enter the same cells again.

Reachability/pathfinding and movement execution are separate responsibilities:

- **reachability/pathfinding** calculates minimum-cost paths, which the movement UI uses for reachable cells and path previews;
- **movement execution** validates the path selected by the caller and charges that path's actual cost.

Execution accepts any valid path whose actual cost is within `remainingMovement`. It does not require the path to be a minimum-cost path and does not run pathfinding to compare against one.

### 15.4 Movement result (§6)

`MovementResult.path: readonly Position[]` is replaced by engine-evaluated transitions:

```ts
interface MovementStep {
    from: Position;
    to: Position;
    cost: number;
}

interface MovementResult {
    state: BattleState;
    steps: readonly MovementStep[];
    cost: number;
}
```

The command expresses the chosen cells. The result expresses what the engine executed, including the cost of each step. When future terrain makes steps cost differently, for example:

```text
A --1--> B --2--> C
```

the per-step costs remain available without the frontend recalculating them. `cost` remains the total charged, and `steps.map(step => step.to)` equals the command's `path`.

Path previews produced by reachability use the same `MovementStep` representation.

### 15.5 MovementError (§8)

The `MovementError` variants stay the same. `INVALID_PATH.reason` is refined from `string` to a literal union, so tests and callers can tell why a path was rejected:

```ts
type InvalidPathReason =
    | 'EMPTY'
    | 'DESTINATION_MISMATCH'
    | 'REVISITED'
    | 'NOT_ADJACENT'
    | 'BLOCKED'
    | 'CORNER_BLOCKED';
```
