# S4.4 Design Contract — Container resource limits

## 1. Purpose and scope

S4.4 is a stage of the observability production rollout. It gives every container that runs on the
production VPS its own resource limits before the observability stack starts there (S6) and the
application is attached to it (S7).

S4.4 sets:
- a memory limit with no swap for all ten containers: the four app containers and the six
  containers of the observability stack;
- a PID limit for all ten;
- `oom_score_adj: 500` for the six stack containers;
- no CPU limits.

It adds the checks that prove these settings are applied, and a manual procedure to apply and roll
back the app's limits on the VPS.

The evidence behind the values is in [VPS_RESOURCE_BUDGET.md](VPS_RESOURCE_BUDGET.md). The stack
itself is described in [OBSERVABILITY.md](OBSERVABILITY.md).

| Containers | Limits in | Combined as |

**Why overlays and not the base files:**
- the values are VPS-specific (one CPU, 4.25 GiB, VPS data), and dev and CI differ;
- retuning would otherwise change dev every time;
- a backend limit in `compose.yaml` would change the dev JVM's heap.

**Consequences:**
- `docker compose up` (dev) and `-f observability/compose.yaml up` load no prod overlay, so dev runs
  without limits.
- On the VPS, every `up` of the stack must include `observability/compose.prod.yaml`. Without it,
  Compose recreates the containers without limits. The documentation in S4.4.2 says so wherever a
  VPS `up` appears.
- The first file passed sets the project directory, so `.env` and the bind mounts resolve as today.

## 4. Rules

### 4.1 Memory (H4)

- **What a limit is**: a containment ceiling, not a reservation.
- **Floor**:
  - at least 2× the highest observed working set (`memory.current − inactive_file`, that is
    `docker stats` MEM USAGE);
  - where a service maps a large binary or data set, at least 1.5× (`anon` + mapped file);
  - always above the configured in-memory components.
- **Raised above the floor** where a phase was not observed.
- **Steps**: 64 MiB below 128 MiB, 128 MiB above.
- **Request-path services** (frontend, cloudflared): one step more.
- **The backend**: chosen by §6.

### 4.2 PIDs (H8)

- The value is **the smallest power of two that is ≥ each of**:
  - 4× the highest observed count;
  - 2× the **upper end** of the configured worst case, where one exists;
  - 128 for Go services (a Go runtime that cannot create a thread aborts the process).
- **Raised one power of two only as a named exception**: where an unobserved phase plausibly creates
  OS threads or processes. Blocking file I/O and child processes do; mmap faults and goroutines do
  not.
- **The app's PID values (S4.4.3) are accepted operational caps, not direct outputs of this rule.**
  - They are backend 1024, postgres 256, frontend 128 and cloudflared 128. §5.1 gives the evidence
    for each.
  - Where one coincides with the rule, as cloudflared's 128 does with the Go floor, it still rests
    on that acceptance, not on the rule.

## 6. Backend memory selection (H3)

**Model** (the measurement approach, "reading B"):
- With a limit L, Java 25 sizes `MaxHeapSize` = L/4 from its cgroup's `memory.max`.
- The pre-upgrade working set of 872 MiB was taken without a limit and without the agent. It does
  not describe the limited configuration.
- WS_est(L) = L/4 + C [ESTIMATE, model]. C is the part of the working set that is not resident Java
  heap:
  - non-heap memory: metaspace, code cache, thread stacks, GC structures;
  - the native memory of the JVM and the agent;
  - active file pages and kernel memory;
  - the probe JVM.
- The model assumes that the resident heap grows to its ceiling L/4 and that C does not depend on L.
- The memory rule L ≥ 2·WS_est(L) is equivalent to **L ≥ 4·C**.

**C as an interval (O4).** The cgroup does not report which of its pages are Java heap, so the
resident heap is bounded instead:
- heap_used ≤ resident heap. Every used heap byte lies in a touched page, and with
  `memory.swap.max` 0 no anonymous page leaves memory.
- Resident heap ≤ heap_committed. Only committed heap can be touched.

For each sample i, with WS_i = `memory.current − inactive_file` and heap readings aligned in time
with it:
- C_low,i = WS_i − heap_committed_i;
- C_high,i = WS_i − heap_used_i.

Over the measurement window, with the probe's overshoot = `memory.peak` − the highest sampled
`memory.current`:
- **C_low = max_i C_low,i + overshoot**;
- **C_high = max_i C_high,i + overshoot**.

**Both are estimates from sampled data, not bounds:**
- They describe the aligned samples only. The interval does not guarantee that it covers every
  unobserved peak of C.
- C_high is not a guaranteed upper bound of the real peak of C, for two reasons:
  - the WS and heap readings of a pair are not simultaneous;
  - C can peak between two samples.
- The overshoot covers this only in part. `memory.peak` records the highest `memory.current`, but
  neither the heap at that moment nor what rose between samples other than through the probe JVM.
- The maximum is taken over every aligned sample, not only the one with the highest WS. So a C that
  peaks at another *sampled* moment is still included.
- The report also gives both values at the highest-WS sample.

**Time alignment:**
- **What is read:** heap_used and heap_committed are the sums over the heap pools of
  `jvm_memory_used_bytes` and `jvm_memory_committed_bytes` (`jvm_memory_type="heap"`).
- **Where and how often:** they come from the main JVM's own metrics endpoint every 5 s, not from
  Prometheus' 15-s scrapes.
- **One clock:** the cgroup sampler and the heap sampler stamp every reading with `/proc/uptime`,
  the same kernel clock in both containers. A heap reading is timed at the midpoint of its fetch.
- **Pairing:** each cgroup sample is paired with the nearest heap reading. A pair more than 2.5 s
  apart is discarded.
- **Reported:**
  - the number of pairs and of discarded samples;
  - the largest time difference within a pair;
  - the largest interval between consecutive cgroup samples, and between consecutive heap readings.

**Assumptions and limits of the estimate:**
- **No page is read directly.** The interval bounds only the heap's share of the working set.
- **C_high is loose right after a collection.** `heap_used` drops at once, while the pages the young
  generation touched stay resident and committed. C_high can then overstate C by up to
  heap_committed − heap_used. This pushes C_high up, but it does not make C_high a guaranteed upper
  bound (see above).
- **A pair is not simultaneous.** Between the two readings the heap changes by allocation and
  collection, so a pair can be off in either direction by what changed within up to 2.5 s.
- **Garbage counts as used.** `heap_used` includes unreachable objects not yet collected. They are
  resident, so the lower bound on the resident heap still holds.
- **C barely depends on L.** Structures sized from the heap (for Serial GC mainly the card table,
  about 1/512 of the heap) grow slightly with L.
- **The run is LOCAL:**
  - one emulated CPU on a 16-CPU host;
  - a run of hours, on development data;
  - the VPS's agent overhead and its long-uptime state are not covered.

**Mapped file pages and C_high' (O6, operator, 2026-11-12):**
- **What the measurement run showed** [LOCAL]:
  - after the window, the main JVM's `smaps_rollup` held 35.2 MiB of resident file-backed pages
    (`Rss − Anonymous`; mostly `libjvm.so`, `classes.jsa`, `lib/modules` and the agent JAR);
  - the backend cgroup's `file` stayed ≤ 0.1 MiB throughout;
  - so those pages were charged to other cgroups. The likely reason is that the image's files were
    already in the page cache from earlier containers or from the pull [inference].
- **Why it matters:**
  - with a cold page cache, for example after a VPS restart, the backend's first touch charges them
    to the backend;
  - whether they then count in the WS depends on whether the kernel keeps them on the active or the
    inactive file list. That was not measured.
- **Sampling, from the confirming run on:**
  - the main JVM's (PID 1) `/proc/1/smaps_rollup` is read every 5 s during the window, stamped with
    `/proc/uptime`;
  - it is read from a helper that shares only the backend's PID namespace;
  - all fields are kept, at least `Rss`, `Pss`, `Anonymous`, `Shared_Clean`, `Shared_Dirty`,
    `Private_Clean` and `Private_Dirty`;
  - readings are paired with the cgroup samples like the heap readings (nearest, ±2.5 s).
- **Per paired sample i:**
  - F_i = Rss_i − Anonymous_i: the main JVM's resident file-backed pages. Shmem is expected to be 0,
    and `Pss_Shmem` is reported;
  - the cgroup's `file_mapped_i`, `active_file_i` and `inactive_file_i` are reported next to F_i, so
    anonymous pages, file pages and the cgroup's own values stay apart.
- **Two variants, both kept apart from the measured WS:**
  - **accounted**: U_acc,i = max(0, F_i − file_mapped_i). Mapped file pages already charged to the
    backend are not added again;
  - **conservative**, which gates: U_cons,i = F_i. Every resident file-backed page of the main JVM
    counts as an extra backend cost. It can double-count at most min(F_i, file_mapped_i,
    active_file_i), and the report gives that bound.
- **C_high' = max_i (WS_i + U_cons,i − heap_used_i) + overshoot**, over the samples that have both a
  heap and an `smaps` pair.
  - C_high (without U) and the accounted variant are reported next to it.
  - WS_eff' = max_i (WS_i + U_cons,i) + overshoot is reported for information.
- **35.2 MiB is not a fixed correction.** Each run uses its own F_i.
- **Not covered:**
  - page cache filled by `read()`, which is not mapped and so not in `smaps`;
  - file pages mapped only by the probe JVM.

## 7. Swap, reservations and CPU (H5, H6, H7)

- **Swap**: `memswap_limit` = `mem_limit` on all ten, so `memory.swap.max` = 0 [S, runc's
  conversion].
  - Why: Docker Desktop (8 GiB of swap), CI and the VPS (host side [UNKNOWN]) then behave the same,
    in line with "never use swap".
  - Consequence: under LXC-wide pressure, a container is killed rather than slowed by swap.
- **Reservations**: none. `mem_reservation` becomes `memory.low`, which its ancestors cap, and
  without swap `anon` cannot be reclaimed anyway.
- **`deploy.resources`**: not used. It has no equivalent of `memswap_limit` or `oom_score_adj`.
- **CPU: S4.4 sets no production CPU limits.** Neither prod overlay has `cpus` or `cpu_shares` for any
  container.
  - The only `cpus` in S4.4 is `cpus: 1` in the local measurement overlay of §10.3(b). It emulates
    the VPS's single CPU for the JVM's ergonomics and is never committed.
  - Why there is no production limit:
    - a `cpus` quota is not work-conserving;
    - on one CPU it would stretch the JVM's start against the 90-s start period and the deploy's
      180-s `--wait`, and WAL replays after a restart;
    - the measured use is small: about 0.07 cores [LOCAL], plus one PSI reading on the VPS.
  - S4.4.2 adds a `DEFERRED_WORK.md` entry "CPU weights":
    - triggers at S6/S7: a slower backend start or deploy `--wait`, sustained per-container
      `cpu.pressure`, or latency degrading with the stack present;
    - first lever: a lower `cpu_shares` on the stack, with the effective `cpu.weight` read, because
      the conversion depends on the runc version.

## 8. OOM behaviour and `oom_score_adj` (H2)

**Two kinds of OOM:**

| | OOM at a container's own `memory.max` | OOM at the LXC's limit |
|---|---|---|
| Candidates | That container's processes only | Every process in the LXC: host services, dockerd, containerd, all ten containers |
| Usual victim | The container's largest process. For the backend, the main JVM, even when the probe tipped it over | The highest badness score: by default the largest process, most likely the backend JVM |
| `oom_score_adj` | No practical effect | Changes the ranking |
| S4.4's limits | They define this event | They do not prevent it. With Σ limits > T, it can happen while every container is below its own limit |
| How it shows | The container's `memory.events.local`: `max`, `oom`, `oom_kill`. Its `memory.events` is equal, since a container cgroup has no children. `docker inspect` `OOMKilled` | `oom_kill` in the victim's cgroup (`memory.events.local`) and in every ancestor (`memory.events`), whichever kernel OOM killer acted. `max` and `oom` only on the cgroup whose limit was hit and its ancestors: if the limit sits above the guest's visible root, they rise nowhere the guest can read. A global host OOM raises no `oom` |

**Linux 5.15 counter semantics** [S]:
- `memory.events` is hierarchical by default;
- `memory.events.local` is local to the cgroup;
- `oom_kill` counts processes of the cgroup killed by any kernel OOM killer;
- **exception**: with the system-wide `memory_localevents` mount option (it can be set only from the
  host's init namespace), `memory.events` carries local counts only. The option shows in the guest's
  cgroup2 line of `/proc/self/mounts`.

**Not visible to the guest:**
- kills outside the guest;
- the outer limit's own `max`, `oom` and `high`;
- throttling by an outer `memory.high`;
- a userspace OOM killer's actions [inference].

**`oom_score_adj: 500` is a process-level preference, never protection:**
- It raises the badness score of each process in a stack container. Containers are not ranked or
  killed as units, as long as no container's cgroup has `memory.oom.group` set and systemd's
  `OOMPolicy` for the container's scope is `continue`. S4.4 sets neither.
  - **runc v1.5.1**, the VPS's version (A.1 (a)), sets none of its own [S, tag `v1.5.1` = commit
    `8f2685a4`, with its vendored `opencontainers/cgroups` v0.0.6]. It writes the file only when the
    container's OCI spec asks for it:
    - a `memory.oom.group` entry in `linux.resources.unified` is written to the cgroup as given,
      with the systemd driver too, when the container is created;
    - an `org.systemd.property.*` annotation, such as `OOMPolicy`, is passed to systemd unchanged,
      and systemd may then set the file.
  - For a container's scope, runc itself sends `Delegate=true` and no `OOMPolicy`.
  - **systemd's `OOMPolicy`** decides what happens to the rest of a scope after an OOM kill [S,
    systemd.scope(5) and systemd.service(5), the current man pages, not the VPS's systemd version]:
    - scope units support it from systemd 253;
    - `continue` only logs the kill, and the unit keeps running;
    - `kill` makes systemd set `memory.oom.group` to 1, so the kernel kills the unit's remaining
      processes too;
    - `stop` makes systemd itself terminate the unit's processes, without `memory.oom.group`;
    - the default is `DefaultOOMPolicy=`, except for units with `Delegate=` turned on, where it is
      `continue`.
  - **Not read from source:** whether Docker puts a `unified` entry or a systemd annotation into the
    spec.
  - **Read on the VPS after the rollout** (A.3, §10.4) [VPS]:
    - systemd 255 (`255.4-1ubuntu8.18`), at or above the 253 from which scope units support
      `OOMPolicy`;
    - each app container has `memory.oom.group` 0, and its scope has `Delegate=yes` and
      `OOMPolicy=continue`.

    So, as read, the condition above holds for the four app containers. The stack's containers are
    read at S6.
- A child process that is killed (a health-check `wget`, a Grafana plugin process, a `docker exec`)
  leaves PID 1 running, under the conditions above. The container does not stop and its restart
  policy does not run; only `oom_kill` and `OOMKilled` record it.
- It does not prevent the LXC from reaching its limit or the reclaim stalls before a kill, which
  slow the backend too.
- It does nothing about the backend's own limit.
- The kernel kills one process per OOM event, and a restarted stack container can grow again.
- It is bypassed by any of these on the provider's host [UNKNOWN]:
  - `memory.oom.group` on the LXC's cgroup;
  - `vm.oom_kill_allocating_task`;
  - a userspace OOM killer;
  - an outer `memory.high`.
- Host processes keep their own values.
- The app's four containers keep the default 0.

## 9. Memory budget

- **Σ limits is not the memory requirement.** 5696 MiB, with the backend at 1792 MiB, is a deliberate
  overcommit against the 4352 MiB of visible RAM.
- **The requirement** is the simultaneous peak H + P + O + K plus the reserve R
  ([Budget model](VPS_RESOURCE_BUDGET.md#budget-model)).
- **T = 4352 MiB** is the best-supported value: LXCFS serves `/proc/meminfo` with exactly the plan's
  size [VPS; the configured limit is an inference]. Its enforcement is [UNKNOWN].
- **If the effective outer limit is lower than 4352 MiB:**
  - the per-container limits are still enforced, because the kernel applies each `memory.max`
    whatever T is;
  - the combined fit is **not guaranteed**;
  - OOM safety is **not guaranteed**: LXC-wide reclaim and OOM come sooner, and can strike while
    every container is below its own limit;
  - the JVM still sizes its heap from its own limit;
  - the design makes no safety claim for this case.
